# 吾身工程开发路线图

这份路线图把竞赛方案转换成可连续交付的工程阶段。每个阶段结束时，都要有一个能运行、能测试、能演示、能回退的版本。

## 开发顺序

```text
阶段 0 工程基线
  -> 阶段 1 本地记录闭环
  -> 阶段 2 AI 网关契约与假实现
  -> 阶段 3 Qwen/DashScope 接入
  -> 阶段 4 来源校验与语义复核
  -> 阶段 5 导出、删除、离线和部署
```

不跳过前一阶段的验收条件。真实模型接入前，必须先证明不依赖外部 API 也能完成前端、网关、错误处理和本地保存的闭环。

## 阶段 0：工程基线

### 目标

三名成员能从同一个干净 checkout 启动项目，知道如何领取任务、使用 AI、提交 PR，并在 GitHub 上保留审查记录。

### Issue 0.1：建立可运行的 React PWA + FastAPI 工程骨架

**目标：** 创建前端和后端目录、启动命令、健康检查和环境变量示例。

**明确不做：** 不接入真实模型、不保存日记、不做登录、不部署到云端。

**验收条件：**

- 干净 checkout 可以安装依赖
- 前端开发服务器可以启动并显示基础页面
- FastAPI 可以启动并返回健康检查结果
- `.env.example` 只包含变量名和说明，不包含密钥值
- 三名成员按同一命令得到相同结果

**测试与验证：** 前端启动检查、后端健康检查、干净目录安装检查。

### Issue 0.2：启用 GitHub 协作保护

**目标：** 配置 `dev` 集成分支、`main` 发布分支、Issue 模板、PR 模板和基础检查。

**明确不做：** 不改变产品功能和业务代码。

**验收条件：**

- `dev` 和 `main` 都不能直接推送
- PR 必须关联 Issue
- PR 模板要求测试、契约、风险和回滚信息
- 三名成员都能从 `dev` 创建分支、推送、审查并合并测试 PR；阶段验收后由集成负责人发布到 `main`

## 阶段 1：本地记录闭环

### 目标

用户可以在没有网络和 AI 的情况下输入、保存、读取和删除原始记录。

### Issue 1.1：定义并实现 IndexedDB 记录层

**目标：** 使用 Dexie 保存和读取符合 `JournalEntry` 契约的记录。

**明确不做：** 不请求后端、不调用 LLM、不做趋势分析。

**验收条件：**

- 保存记录后可以按 ID 读取
- 刷新页面后记录仍然存在
- 删除记录后不能从应用查询到
- 空白内容被拒绝
- 数据包含 `schemaVersion`

**测试：** Dexie 数据层单元测试和空内容边界测试。

### Issue 1.2：实现记录页面和“收到”确认

**目标：** 提供移动端优先的输入、提交和列表查看流程。

**明确不做：** 不显示 AI 分析、不显示连续打卡、不请求网络。

**验收条件：**

- 输入内容后可以提交
- 提交后显示简短确认
- 原文在列表中可查看
- 页面刷新后内容仍然存在
- 网络不可用时仍能完成保存

**测试：** Vitest 组件测试和 Playwright 本地记录流程测试。

### 阶段门

只有当 Issue 1.1 和 1.2 的测试通过，并能在演示环境完成一次离线记录，才进入阶段 2。

## 阶段 2：AI 网关契约与假实现

### 目标

先验证前端、FastAPI、结构化响应和本地保存之间的对接，不依赖真实 Qwen API。

### Issue 2.1：建立 Pydantic 模型和 OpenAPI 输出

**目标：** 用 `JournalEntry`、`OrganizeRequest`、`OrganizeResult` 和 `ErrorResponse` 建立 FastAPI 输入输出模型。

**明确不做：** 不调用 DashScope，不实现语义校验。

**验收条件：**

- FastAPI 自动生成的 OpenAPI 与 `CONTRACTS.md` 一致
- `consent=false` 的请求被拒绝
- 无效字段返回约定错误结构
- 生成的前端类型可以被项目导入

**测试：** Pytest API 契约测试和 OpenAPI 快照或结构检查。

### Issue 2.2：实现可替换的假网关

**目标：** 提供固定、可重复的 `OrganizeResult`，让前端先完成整理流程。

**明确不做：** 不连接真实模型，不把假数据伪装成真实分析。

**验收条件：**

- 用户明确选择并确认后才发送请求
- 假网关结果可以在前端展示并保存到本地
- 超时和无效结构可以触发错误状态
- 原始记录在任何失败路径都保留

**测试：** 前后端集成测试和失败路径 Playwright 测试。

### 阶段门

没有真实 API 密钥时，也能演示“选择记录 → 确认 → 网关返回结构化结果 → 本地保存 → 查看证据”的完整流程，才进入阶段 3。

## 阶段 3：Qwen/DashScope 接入

### 目标

在保持假网关可替换的前提下接入真实结构化输出模型。

### Issue 3.1：实现 DashScope 适配器

**目标：** 用 HTTPX 调用 Qwen-Plus，并把外部响应映射到 `OrganizeResult`。

**明确不做：** 不改变前端公共契约，不把 API 响应原样传给浏览器。

**验收条件：**

- API 密钥只从环境变量读取
- 请求设置超时和明确的失败映射
- 模型返回无法解析时返回 `INVALID_MODEL_OUTPUT`
- 外部 API 失败时原始记录不丢失
- 本地测试可以替换为假适配器

**测试：** HTTPX 模拟响应测试、超时测试和无效 JSON 测试。

### Issue 3.2：接入用户确认流程

**目标：** 在界面上明确显示将发送的记录和确认动作。

**明确不做：** 不自动发送全部本地记录，不在记录模式调用模型。

**验收条件：**

- 用户可以查看选中的文本
- 未确认时不会发生网关请求
- 取消确认不会改变原始记录
- 请求失败后可以重试而不重复创建原始记录

## 阶段 4：来源校验与语义复核

### 目标

让 AI 结果可追溯，并阻止无法由原文支持的结论进入最终结果。

### Issue 4.1：实现确定性来源校验

**目标：** 检查每个 `InsightItem` 是否引用参与本次整理的记录和原文片段。

**明确不做：** 不用关键词匹配冒充完整语义判断，不修改用户原文。

**验收条件：**

- 不存在的 `entryId` 被拒绝
- 找不到的引用片段被拒绝
- 偏移量非法被拒绝
- 所有保留结论都有 `evidence`
- 校验失败返回可重试错误且原始记录保留

**测试：** 合法引用、错误引用、跨记录引用和多字节文本边界测试。

### Issue 4.2：实现事实/推断标记和样本不足处理

**目标：** 保留 `fact`/`inference` 区分，在证据不足时返回明确状态。

**明确不做：** 不把推断改写成事实，不为了填满模块生成内容。

**验收条件：**

- `fact` 和 `inference` 都有来源证据
- 空模块可以保持为空
- 样本不足时界面不会显示确定性结论
- 语义复核失败时结果不能进入已保存结果列表

## 阶段 5：数据主权、PWA 和部署

### 目标

补齐导出、删除、离线体验和可演示部署。

### Issue 5.1：导出和删除本地数据

**验收条件：**

- 所有本地记录和整理结果可以导出为可读取文件
- 删除确认后本地记录和结果不可从应用读取
- 导出失败不会删除原始数据
- 测试使用虚构数据

### Issue 5.2：离线记录和 PWA 安装能力

**验收条件：**

- 断网时可以打开已缓存页面
- 断网时可以保存新记录
- 恢复网络不会自动发送未确认内容
- 安装提示和图标配置可在目标浏览器验证

### Issue 5.3：部署演示环境

**验收条件：**

- 前端和 FastAPI 的启动或部署方式写入 README
- 密钥通过部署环境变量注入
- 健康检查可访问
- 三名成员能从最新标签复现实验流程

## 阶段门规则

每个阶段结束前必须完成：

1. 所有本阶段 Issue 的验收条件
2. 对应单元、接口或端到端测试
3. 一次三人共同运行的演示
4. 一份已知风险和未决事项记录
5. 一个可回退的 Git 标签

没有通过阶段门时，不进入下一阶段；先修复或记录决定。
