# 人工协作手册

## 人负责的决定

用户负责最终决定：

- 比赛版的产品目标、范围和延期功能。
- 公共 API、数据格式、证据规则和兼容性取舍。
- 是否接受已知风险，以及是否改变已批准的技术决定。
- Pull Request 是否达到验收条件并可以合并到 `dev`；用户可以明确委托审查者在审查通过后决定并执行合并。
- 阶段验收通过后是否发布到 `main`。

AI 可以起草实现、测试和文档，但不能自行扩大范围、直接推送 `dev` 或 `main`、未经用户授权合并 PR、暴露密钥，或把未验证结果描述为完成。

## 什么时候提供方案

只有以下问题需要用户在多个方案中选择：

- 产品方向和比赛演示范围。
- 公共接口或数据格式的变化。
- 会影响前后端边界、验收标准或延期功能的技术取舍。

实现细节、文件拆分、测试命令和提交信息由 AI 按现有代码风格处理；如果实现中发现问题会先报告事实和影响。

## 决策输入格式

涉及大方向时，AI 应提供：

1. 当前事实和代码证据。
2. 两到三个可执行方案及其影响。
3. 推荐方案和推荐理由。
4. 对比赛版范围、接口和测试的影响。

用户选择后，AI 才能把选择写入 `docs/engineering/DECISIONS.md`。建议不能写成已批准决定。

## 审查和合并

- 每个任务先绑定一个 GitHub Issue，Issue 写清目标、边界和验收条件。
- 功能分支通过 Pull Request 合并到 `dev`；`main` 只接收阶段验收后的可演示版本。
- 至少另一名成员检查代码、测试和范围；发现意见时先处理并重新验证。
- 合并前必须确认没有 `.env`、真实日记、依赖目录、构建产物或测试缓存。
