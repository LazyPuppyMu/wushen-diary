# 吾身团队协作手册

这份手册给三名项目成员使用。它解释谁做什么、任务如何进入开发、GitHub 如何记录过程，以及什么时候必须停下来讨论。

## 1. 先记住四条规则

1. 人决定目标、范围、接口、验收和是否合并。
2. AI 负责起草实现、测试和说明，输出必须经过验证。
3. 一个 Issue 只描述一个可以独立验证的结果。
4. `dev` 是集成分支，`main` 是可演示发布分支；两者都只接受经过审查的 Pull Request。

完整工程事实以 `PROJECT_BASELINE.md` 为准；本手册只规定团队怎么工作。

## 2. 三个角色

每个迭代开始时明确当周负责人。角色可以轮换。

### 集成负责人

- 维护 `dev` 集成分支、`main` 发布分支和版本标签
- 检查 Issue 之间是否有接口冲突
- 审核 PR 是否能合并
- 发布三个人都能运行的版本
- 发生冲突时组织决策记录

### 功能负责人

- 领取一个端到端功能
- 与 AI 一起实现页面、数据调用和测试
- 保持变更局限在当前 Issue
- 在 PR 中说明验收结果和未解决问题

### 质量与 AI 负责人

- 维护测试数据和测试命令
- 检查 AI 网关、结构化输出和错误处理
- 复核隐私、密钥和真实数据风险
- 审查功能负责人提交的 PR

角色不代表只有一个人能修改某个目录。任何人都可以提交 PR，但不能自己批准自己的高风险变更。

## 3. 如何拆任务

一个任务必须能在一次短迭代中完成、测试并演示。优先按用户可感知的“垂直切片”拆分，也就是从入口到数据保存或展示都包含在内的一小段完整功能。

每个 Issue 必须回答：

- **目标：** 完成后用户或系统能做什么？
- **明确不做：** 这次刻意不包含什么？
- **输入：** 任务从哪里拿到数据？
- **输出：** 任务提供什么结果？
- **允许修改的文件：** 哪些目录和文件可以改？
- **验收条件：** 怎样观察到任务完成？
- **测试命令：** 用什么命令验证？
- **依赖：** 需要先完成什么？
- **回滚：** 出问题时如何回到上一个版本？

如果一个任务同时包含多个独立结果，就拆成多个 Issue。不要把“完成整个 PWA”“接入全部 AI 能力”当成一个任务。

## 4. Git 和 GitHub 的最小工作流

```text
dev
  -> 为 Issue 创建功能分支
  -> 在本地修改和测试
  -> 提交小而清楚的 commit
  -> 推送分支到 GitHub
  -> 向 dev 创建 Pull Request
  -> 另一名成员审查
  -> 检查通过后合并 dev
  -> 三个人同步并验证
  -> 阶段验收通过后向 main 发布并创建标签
```

### 常用命令

在仓库根目录执行：

```powershell
git switch dev
git pull --ff-only origin dev
git switch -c feature/<issue-id>-<short-name>
git status
git add <修改过的文件>
git commit -m "feat: <简短描述>"
git push -u origin feat/<issue-id>-<short-name>
```

完成推送后，到 GitHub 向 `dev` 创建 Pull Request，关联对应 Issue。不要直接在 `dev` 或 `main` 上工作，也不要用一个分支同时承载多个不相关任务。

### 分支命名

- 新功能：`feature/<issue-id>-<short-name>`
- 修复问题：`fix/<issue-id>-<short-name>`
- 文档规则：`docs/<issue-id>-<short-name>`

### Commit 规则

一次 commit 表示一个可理解的变更。提交信息说明动作和对象，例如：

```text
feat: save journal entry locally
test: cover empty entry validation
docs: clarify AI task protocol
```

## 5. Pull Request 审查

提交 PR 前，功能负责人自己先检查：

- 是否满足 Issue 的每一条验收条件
- 是否只修改了当前任务需要的文件
- 是否更新了必要的测试和接口文档
- 是否运行并记录了测试命令和结果
- 是否包含密钥、真实日记或调试输出
- 是否说明了已知限制和回滚方式

审查者重点检查：

1. 需求和代码是否对应
2. 输入输出是否符合 `CONTRACTS.md`
3. 错误是否会让原始记录丢失
4. AI 结果是否经过结构化校验和来源验证
5. 是否有不属于当前 Issue 的改动
6. 测试是否真的覆盖验收条件

有以下情况时拒绝合并并要求先讨论：

- 改变技术栈、公共接口或数据格式
- 需要新增依赖但没有说明原因
- 测试失败且原因不明确
- 删除或迁移用户数据
- 发现代码与权威文档冲突
- AI 修改范围超出 Issue

## 6. 与 AI 一起工作

把任务写成 Issue 后，再把同样的边界交给 AI。每次对话都要求 AI：

1. 先读取项目入口、基线、当前 Issue 和相关契约
2. 复述目标和明确不做的内容
3. 列出准备修改的文件和风险
4. 只做当前任务的最小改动
5. 运行测试并报告结果
6. 说明尚未验证的假设

不要用“把整个项目写出来”“顺便优化全部代码”作为任务描述。遇到架构或接口选择时，由人写决策记录，AI 按已批准的决定实现。

## 7. 每日和每次合并前的沟通

每天同步一次，每个人只回答三件事：

- 我完成了哪个 Issue 或子步骤？
- 我遇到了什么阻塞，证据是什么？
- 我接下来需要谁做什么？

每次合并后，三个人都从最新 `dev` 拉取并运行启动命令。阶段验收通过后再同步 `main` 发布版本。不要让一个人的本地版本长期成为“唯一能运行的版本”。

## 8. 出现问题时如何处理

1. 先停止继续叠加改动，保留当前分支和测试输出。
2. 判断问题属于需求、接口、实现、环境还是数据。
3. 在 Issue 或 PR 中记录可复现步骤和实际结果。
4. 如果影响公共契约或架构，新增决策记录。
5. 优先回退到上一个可运行标签，再单独修复问题。

不能通过“让 AI 再试一次”代替定位原因。每次重试都必须有新的假设和验证方式。

- [ ] 安装项目要求的运行环境
- [ ] 按 README 启动前端和后端
- [ ] 在本地完成一次健康检查或示例流程
- [ ] 阅读一个待处理 Issue
- [ ] 创建自己的任务分支
- [ ] 用 AI 工作手册中的模板开始一次小任务
- [ ] 运行测试并创建一个草稿 PR
- [ ] 让另一名成员审查后再合并
